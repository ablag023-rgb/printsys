# Спецификация: Система печати судебных дел

**Версия:** 3.0 · **Дата:** 2026-09-02 · **Статус:** архитектура зафиксирована, часть вопросов открыта

История версий:
- **1.0** — HTML-прототип (client-side, File System Access API). Реализован, `printsys.html`
- **1.5** — серверное веб-приложение (FastAPI + HTMX + PG + Docker). Реализовано
- **2.0** — серверный сканер файловой шары + Windows-клиент печати. Сканер реализован, клиент — нет
- **3.0** *(этот документ)* — **документы в нескольких S3-хранилищах**, сервер хранит ссылки, клиент авторизуется и печатает. Основание: четыре экспертные проработки от 2026-09-02

---

## 1. Context

Оператор юрслужбы готовит пакеты документов для подачи в суд по долгам ЖКУ. Единица работы — **дело**, ключ = код КСР.

Якорь дела — «Справка о расчетах по ЖКУ» (xlsx), КСР = первое число в её имени с обрезанными нулями. К делу цепляются все документы, содержащие КСР в имени (`3455945` или `0003455945`). Документы раскладываются по настраиваемым слотам; **порядок слотов = порядок листов в PDF** — критично, листы сшиваются. На каждой странице подвал `КСР/НомерЛиста`, первым идёт титульный лист с описью.

### Что изменилось в 3.0

Документы лежат **не на файловой шаре, а в нескольких S3-хранилищах** — каждая система-источник пишет в своё. Сервер их индексирует, собирает дела и **хранит ссылки на объекты**, а не файлы. Клиент **авторизуется** на сервере, получает ссылки, **сам забирает объекты из S3** и печатает через локальный сервер печати.

### Реальные тестовые данные

`C:\Users\ab\Desktop\Доки2` — 26 файлов, 6 МБ, 7 дел, 2 папки по ФИО должника:

| Префикс | Что | Пример |
|---|---|---|
| `da_*` (xlsx) | Справки о расчётах — **якоря дел** | `da_0003455945_Справка о расчетах по ЖКУ - для суда 8656afd3-….xlsx_5414620_.xlsx` |
| `dl_*` (pdf) | Выписки ЕГРП, платёжные поручения | `dl_0003455945_Выписка ЕГРП_1429521.pdf` |
| `50288xxx_*` (pdf) | Прочее | `50288241_3455945_67123124_10448.pdf` |

**Дело 3455967 намеренно неполное** — платёжка есть, выписки ЕГРП нет. Естественный тест-кейс, не «чинить».

## 2. Целевая архитектура

```
┌── S3 «Биллинг» ──┐  ┌── S3 «Документооборот» ──┐  ┌── S3 «Архив сканов» ──┐
│  ksr-spravki     │  │  ksr-pravoustanav        │  │  ksr-prochee          │
│  da_*.xlsx       │  │  dl_*.pdf                │  │  50288xxx_*.pdf       │
└────────┬─────────┘  └───────────┬──────────────┘  └──────────┬────────────┘
         │  list_objects_v2 + GET только справок              │
         └──────────────────┬─────────────────────────────────┘
                            ▼
        ┌─ Сервер (FastAPI + PostgreSQL) ──────────────────┐
        │  ИНДЕКСАТОР — единственный, каждые 5–10 мин      │
        │  РЕЕСТР дел, статусы, история, аудит             │
        │  НАСТРОЙКИ: доступы к N хранилищам, слоты        │
        │  АУТЕНТИФИКАЦИЯ: JWT, роли, presigned-выдача     │
        │  ФАЙЛОВ НЕ ХРАНИТ И НЕ РЕТРАНСЛИРУЕТ             │
        └───────────────┬──────────────────────────────────┘
                        │ HTTPS: дела + presigned URL
                        ▼
        ┌─ Клиент (Windows, у оператора) ──────────────────┐
        │  вход по логину, токен в Credential Manager      │
        │  качает объекты из S3 НАПРЯМУЮ по presigned      │
        │  Excel COM → PDF, сборка дела, подвал КСР/NN     │
        │  win32print → локальный сервер печати → принтер  │
        └──────────────────────────────────────────────────┘
```

Три свойства: **один индексатор** (нет гонок), **файлы не через сервер** (нет двойного пробега), **аудит на сервере** (журнал выдачи ссылок знает, кто и что скачал).

## 3. Индексация нескольких S3

### 3.1. Обнаружение изменений: ETag как opaque-маркер версии

В S3 нет ни `mtime`, ни `inode`. Признак изменения — кортеж **`(etag, size)`**.

| Признак | Надёжность | Стоимость | MinIO | Подводные камни |
|---|---|---|---|---|
| `Size` | низкая одна | 0 (в LIST) | да | правка xlsx часто даёт тот же размер |
| `LastModified` | средняя | 0 (в LIST) | да | секундная гранулярность; перезалив копии обновляет дату без смены содержимого → ложные перепарсинги |
| **`ETag`** ✅ | **высокая как маркер версии** | 0 (в LIST) | да | при multipart — `md5-of-md5s-N`, зависит от размера части и клиента; при SSE вообще не хэш |
| `VersionId` | наивысшая, если versioning вкл. | 0 | да | другой API, нет у старых объектов |
| `ChecksumSHA256` | наивысшая | **+1 HeadObject на объект** | частично | не заполнен, если писатель не запросил |

**ETag берём как opaque-токен, а не как md5.** Нам не нужно, чтобы он был хэшем — нужно лишь, чтобы менялся при перезаписи, а это S3 гарантирует. `LastModified` в триггер изменения **не включаем**: ночной перезалив «всё заново» прыгал бы датой без смены содержимого.

### 3.2. Кеш парсинга по ETag убирает проблему переименований

В файловой модели (v2.0) переименование папки по ФИО меняло путь всех файлов и вызывало массовый перепарсинг; лечилось инвариантом по inode. **В S3 это не нужно.**

Кеш распарсенных справок живёт в отдельной таблице с ключом `content_etag`, **не привязанной к ключу объекта**. Переименование = copy+delete → новый ключ, но **тот же ETag** → парсинг переиспользуется бесплатно. Логика `file_key`/inode **выбрасывается целиком** — это строго проще и надёжнее.

### 3.3. Полный листинг каждый цикл

`list_objects_v2` через пагинатор boto3, 1000 ключей на страницу. 20 000 объектов ≈ 20 запросов ≈ 1–3 с; 200 000 ≈ 200 запросов ≈ 10–30 с. На AWS 200k объектов при скане раз в 5 минут ≈ **$0.29/сутки на бакет**; в MinIO бесплатно.

Параллелизм: **asyncio + aioboto3, одна задача на хранилище**, глобальный `Semaphore(4)`. Нагрузка I/O-bound, отдельные процессы не нужны.

**Отвергнуто:**
- **S3 Inventory** — сутки лага, нет в MinIO
- **`StartAfter`** — ключи лексикографические, не хронологические: новый файл может лечь в начало и потеряться
- **Нотификации (EventBridge/SQS, MinIO webhook)** — семантика at-most-once, события теряются; и только листинг видит **удаления**. Оставляем как опциональный ускоритель — триггер внеочередного скана, **никогда как источник истины**

### 3.4. Скачивание только справок

Качать нужно лишь `da_*.xlsx` — это ~25% объёма. Порядок: по `etag` смотрим кеш → hit, ничего не качаем; miss → `get_object` целиком во временный файл на tmpfs (`/dev/shm`, ~200 КБ), парсим, удаляем в `finally`.

Range-запросы для xlsx не оправданы: zip-каталог в конце, получится 2 GET вместо 1 ради экономии килобайт.

### 3.5. Защита от ложных orphan ужесточается

Правило v2.0 «обрыв связи не помечает дела потерянными» уточняется:

> `last_seen_scan_id` продвигается и `is_orphaned` выставляется **только для хранилищ, чей листинг завершился полностью** — последняя страница получена, `IsTruncated=false`.

Хранилище со статусом `unreachable`/`auth_error` **полностью исключается** из orphan-фазы; его объекты остаются в БД, дело помечается «источник недоступен».

boto3: `Config(connect_timeout=5, read_timeout=30, retries={'max_attempts':5,'mode':'adaptive'})`. `NoSuchBucket`/`InvalidAccessKeyId` не ретраить — сразу в `health`.

### 3.6. Что упрощается в S3 относительно файловой модели

**Проблема «файл залит наполовину» исчезает.** Multipart-объект появляется в листинге только после `CompleteMultipartUpload` — атомарно. Значит **не нужны** ни `pending_locked`, ни фильтр lock-файлов Excel `~$`.

Консистентность: AWS S3 с декабря 2020 — strong read-after-write, включая LIST. MinIO — строго консистентен на одном узле и в erasure-set. Совместимые (Ceph RGW, Yandex/VK) — уточнить, см. §10.

## 4. Авторизация клиента и доступ к объектам

### 4.1. Presigned URL, выдаваемые пачками

| Способ | Файлы через сервер? | Ротация секретов | Аудит | Риск утечки | MinIO |
|---|---|---|---|---|---|
| **Presigned URL** ✅ | нет | ключи только на сервере | полный, серверный журнал | средний → снижается TTL | да |
| Прямые креды у клиента | нет | **плохо**: ключ на 5–20 машин | нет, всё под одним ключом | высокий: кража = весь бакет | да |
| STS AssumeRole | нет | автомат | средний | низкий | да, урезанный |
| Прокси через сервер | **да** | ключи на сервере | полный, пофайловый | низкий | да |

**Решение:** presigned GET, **TTL 15 минут**, выдача **пачками по 50–100 объектов** через `POST /api/v1/files/presign`.

Проблема «пакет печатается 20 минут, ссылки протухнут» снимается не длинным TTL, а порционной выдачей: клиент запрашивает свежие ссылки перед каждой порцией дел, ссылка живёт от запроса до скачивания — секунды. При 403 — один автоматический re-presign, потом ошибка дела.

**STS отклонён:** даёт мультитенантную изоляцию, которой у нас нет (один класс операторов), но требует настройки policy в каждом хранилище.

**Прямые креды отклонены:** ротация означает обход всех машин, аудит обезличен.

**Прокси-режим — аварийный флаг `file_delivery=proxy`**, не по умолчанию. Оправдан, если S3-endpoint недоступен с клиентских подсетей (сегментированная сеть) или СБ требует пофайловый аудит с гарантией доставки. Объёмы позволяют: 100 дел × 5 файлов × 1 МБ = 500 МБ.

### 4.2. Публичный и внутренний endpoint — разные

**Стык, который легко пропустить.** Сервер ходит в хранилище по внутреннему адресу (`http://s3-billing:9000` внутри compose-сети или во внутреннем сегменте), а **presigned-ссылка подписывается под конкретный хост** — по внутреннему адресу она у оператора не откроется.

Поэтому у хранилища **два поля**: `endpoint_url` (для индексатора) и `public_endpoint_url` (для подписи ссылок клиенту). Если второе пусто — используется первое. Несовпадение — типовая причина «у меня ничего не качается», выносится в диагностику.

### 4.3. Аутентификация: JWT + ротируемый refresh

Логин/пароль (argon2id) → access-JWT 30 мин (только в памяти) + opaque refresh 30 дней. Refresh **ротируемый**: использование старого токена = признак компрометации, отзывается вся цепочка (`family_id`).

**Хранение на клиенте:** refresh в **Windows Credential Manager** (шифрует через DPAPI под учёткой пользователя). Access — в памяти. Пароль на диск не пишется никогда.

Kerberos/OIDC дали бы SSO, но требуют IdP и reverse-proxy с `mod_auth_gssapi` — недели работы при одном разработчике. Отложено в фазу 2.

**Роли:** `operator` (дела, presign, печать), `supervisor` (+ аудит всех), `admin` (настройки хранилищ, пользователи).

### 4.4. Аудит доступа к персданным

В файловой модели аудит давал файловый сервер — доступ шёл под доменной учёткой оператора. **В S3 этого нет.**

Источник истины — **серверный журнал выдачи presigned-ссылок**: только он знает `user_id`, `case_id`, `object_key`, `client_ip`, время. S3 access logs включаются дополнительно, но там виден лишь серверный ключ — годятся как контроль «не было ли доступа мимо сервера».

Достаточная пара для юрслужбы: `file_access_log` (кому выдан доступ к документу должника) + `print_history` (кто и когда напечатал дело). Хранение — 3 года (уточнить, §10).

### 4.5. Снижение риска утечки ссылок

Presigned URL — bearer-токен в URL: попал в лог прокси или скриншот, и любой скачает документ.

**Работает:** TTL 15 мин (главное), HTTPS-only, `response-content-disposition=attachment`, ссылка живёт только в памяти desktop-клиента (не в браузере), маскирование `X-Amz-Signature` в логах reverse-proxy.

**Привязка к IP отклонена:** для presigned переносимо не работает (только через policy-условие в STS), ломается на NAT/VPN.

**Одноразовость:** S3 не умеет. Эмулируется счётчиком в `file_access_log` — это не запрет, а детект: повторный ход по тому же `presign_id` с другого IP → алерт.

### 4.6. Работа при недоступности

Клиент кеширует скачанное и собранный PDF в `%LOCALAPPDATA%\printsys\cache`: TTL 24 часа, шифрование DPAPI, затирание при выходе. Позволяет допечатать пакет при падении S3.

Отчёты о печати при недоступном сервере — в локальную очередь `outbox.jsonl` с досылкой, иначе теряется аудит.

## 5. Подсистема печати

### 5.1. «Локальный сервер печати» — клиенту всё равно

Для `win32print` любая очередь это имя: `OpenPrinter("\\\\printsrv\\HP-01")` и `OpenPrinter("HP-01")` работают одинаково, спулер сам делает RPC. **Код клиента идентичен для всех вариантов**, различаются эксплуатация и диагностика.

| Вариант | Выбор принтера | Per-job DEVMODE | Наблюдаемость |
|---|---|---|---|
| **Windows Print Server (AD)** — вероятный | `ENUM_CONNECTIONS`, имя `\\srv\Q` | работает; лотки зависят от драйвера **на сервере** | `GetJob` через RPC, может блокировать поток |
| Локальный принтер USB/TCP | `ENUM_LOCAL` | лучший контроль | лучшая: SNMP по порту |
| CUPS рядом | как AD (виден как IPP-очередь) | зависит от PPD | худшая: Windows не видит статусы CUPS |
| Свой агент-очередь | — | — | **не делать**: дублирует спулер |

**Обязательно оба флага:** `EnumPrinters(PRINTER_ENUM_LOCAL | PRINTER_ENUM_CONNECTIONS)` — иначе сетевые очереди, подключённые к пользователю, не попадут в список.

### 5.2. Окно вместо чанков

Не «пачками по 50», а **скользящее окно 3–5 незавершённых заданий**: отправили дело → дождались исчезновения из `EnumJobs` → шлём следующее.

Даёт естественный backpressure, ограничивает потери при замятии (максимум N дел «в воздухе»), делает паузу мгновенной. Сто дел по 10 листов — сотни мегабайт EMF в спулере, очередь без окна упирается в диск.

Опрос: `FindFirstPrinterChangeNotification` (событийно, не пропускает короткие переходы), `GetJob` как fallback раз в секунду **в отдельном потоке** — RPC к мёртвому принт-серверу висит минутами.

Ошибка (`JOB_STATUS_ERROR / PAPEROUT / OFFLINE / BLOCKED_DEVQ`) → **пауза всего пакета**, не пропуск дела: порядок важен оператору, рвать нельзя.

### 5.3. `JOB_STATUS_PRINTED` не означает «напечатано»

Это сигнал **передачи в порт**; спулер физику принтера не опрашивает, а задание после завершения исчезает из очереди — терминальное состояние можно и не увидеть.

Иерархия доверия:
- `ERROR / PAPEROUT / OFFLINE` — **верить** (позитивный сигнал сбоя)
- `DELETED` — верить
- исчезновение без ошибки → **`SENT`** (гипотеза «ушло»), **не `PRINTED`**
- счётчику страниц — не верить

Финальный `PRINTED` ставит **человек**, приняв стопку. Опционально SNMP-счётчик страниц — только если принтеры однородные.

### 5.4. Один job на дело, лотки через `ResetDC`

Разные слоты могут требовать разных лотков (оригинал/копия) и дуплекса. **Разбивать дело на несколько заданий запрещено** — теряется атомарность отката и рвётся порядок листов на общем принтере.

Решение: один job на дело, DEVMODE фиксируется на уровне дела, `DefaultSource`/`Duplex` переключаются через `ResetDC` между документами внутри задания (после `EndPage`).

DEVMODE строить **только тройным вызовом `DocumentProperties`** (`0` → правка полей + `Fields` → `DM_IN_BUFFER|DM_OUT_BUFFER`) — руками структуру не собирать, там приватные данные драйвера. Поддержку значений проверять `DeviceCapabilities(DC_BINS/DC_DUPLEX)` и **валидировать конфиг слотов на старте пакета**, а не падать на 40-м деле.

Печать PDF — GDI-путь (`CreateDC/StartDoc/StartPage`) через pypdfium2, не raw `WritePrinter`.

### 5.5. Виртуальный принтер для тестов

**«Microsoft Print to PDF» для автотестов не годится.** Порт `PORTPROMPT:` **по замыслу** показывает диалог сохранения; подмена порта на `FILE:` даёт `.prn` или тишину; Microsoft прямо отвечает, что silent-печать с автоименованием не поддерживается.

| Принтер | Диалог | Годен для автотестов | Путь вывода |
|---|---|---|---|
| MS Print to PDF | **всегда** | нет | не задаётся |
| MS XPS Document Writer | да | нет | — |
| PDF24 / CutePDF | по умолчанию да | частично | INI/реестр |
| **Bullzip / PDFCreator** ✅ | нет в auto-save | **да** | runonce-INI: `Output=`, `ShowSaveAS=never` |
| `FILE:`-порт + PostScript | нет | да (fallback) | `pOutputFile` в `DOC_INFO_1` |

### 5.6. Разрез тестирования

Шов: **«сборка PDF» ⟂ «отправка в спулер»**.

- **Кроссплатформенно и по-настоящему:** сборка PDF — порядок слотов, титул с описью, подвал `КСР/лист` на каждой странице, число страниц. Это ~90% логики и **100% рисков сшивания**
- **Мокается:** `win32print` целиком за интерфейсом `PrintBackend` (`list_printers/submit/poll`). Фейк воспроизводит замятие, offline, отмену
- **Интеграционный smoke** на Windows-агенте — Bullzip в auto-save

CUPS + `cups-pdf` для Linux-CI **не окупается**: проверяет CUPS, а не Windows-спулер и не DEVMODE.

### 5.7. Очередь дел на клиенте

Нужна — но **очередь дел, а не заданий** (спулер уже есть, дублировать нельзя).

SQLite на клиенте, состояние пишется **до** `StartDoc`. Переживает перезапуск: при старте items в `SENDING` сверяются с `EnumJobs`; не найдено → `AMBIGUOUS`, решает оператор.

```
                    ┌──────────┐
   собран PDF  ───► │  QUEUED  │◄──── retry ────┐
                    └────┬─────┘                │
            окно 3–5   ▼                        │
                    ┌──────────┐  исключение    │
```

## 6. Модель данных

```sql
-- Хранилища (замена sources)
storages(id, name, kind,
         endpoint_url,            -- для индексатора
         public_endpoint_url,     -- для подписи presigned клиенту (§4.2)
         region, bucket, prefix,
         access_key, secret_key_enc,      -- Fernet, в API не отдаётся
         addressing_style, verify_ssl, enabled,
         health,                  -- ok | auth_error | unreachable
         health_error, last_ok_scan_at)

-- Объекты (замена source_files)
source_objects(id, storage_id FK, key, name,
               size, last_modified, etag, version_id,
               ksr, doc_kind,
               last_seen_scan_id, state,
               UNIQUE(storage_id, key))

-- Кеш парсинга по содержимому, НЕ по ключу объекта (§3.2)
parsed_docs(content_etag PK, parser_version, parsed_meta jsonb, parsed_at)

-- Дела: собираются по ksr ПОВЕРХ всех хранилищ
cases(ksr PK, date_formed, account, period, provider, service,
      slots jsonb,             -- {slot_id: [{storage_id, key, name, size, etag}]}
      composition_hash,        -- хэш [(slot_id, storage_id, key, etag)]
      status, cycle_no, assignee_id, claimed_at,
      is_stale, is_orphaned, printed_at, submitted_at,
      last_seen_scan_id, first_seen_at, updated_at)

-- Аутентификация
users(id, login UNIQUE, full_name, pwd_hash, role, is_active, last_login_at)
devices(id, user_id FK, device_id UUID, hostname, os_user, last_seen)
refresh_tokens(id, user_id FK, device_id FK, token_hash UNIQUE, family_id UUID,
               issued_at, expires_at, revoked_at, revoked_reason, replaced_by)

-- Аудит
file_access_log(id, user_id FK, device_id FK, case_id, storage_id FK, object_key,
                presign_id UUID, issued_at, expires_at, client_ip,
                downloaded_at, bytes, http_status)     -- PARTITION BY month
print_history(id, user_id FK, case_id, printer, copies, duplex, tray,
              pages_total, files_snapshot, started_at, finished_at,
              status, error, batch_id UUID, reason)
audit_log(id, user_id FK, action, object_type, object_id, before jsonb, after jsonb, at, ip)
scan_runs(id, storage_id FK, trigger, started_at, finished_at, status,
          objects_seen, objects_new, objects_changed, objects_missing,
          parsed_count, cases_new, cases_updated, cases_orphaned, duration_ms, error)
```

**Ключевое:** `source_objects` не знает о делах. Сборка идёт запросом `WHERE ksr = :k` **без фильтра по хранилищу** — мультибакетность получается бесплатно, дело собирается из объектов разных S3.

## 7. Локальная симуляция: три MinIO

### 7.1. Почему три контейнера, а не один с тремя бакетами

Только отдельные контейнеры честно моделируют **разные endpoint'ы и разные учётные данные** — а именно это должен уметь хранить сервер. И только так воспроизводится кейс «одно хранилище лежит, остальные работают».

| Инструмент | Несколько endpoint'ов | Вес | Совместимость | Годится для CI |
|---|---|---|---|---|
| **MinIO ×3** ✅ | да, честно | 150–250 МБ each | очень высокая | да, старт ~2 с |
| MinIO ×1, 3 бакета | нет | минимум | та же | да |
| LocalStack | через отдельные контейнеры | 0.5–1 ГБ | креды всегда `test/test` | тяжеловат |
| gofakes3 / s3proxy | да | очень лёгкий | частичная, нет versioning | да |

Порты выбраны без конфликта с занятыми (`web` 8001, `db` 5433): API **9101–9103**, консоли **9191–9193**.

### 7.2. Раскладка документов

| Документ | Префикс | Хранилище / бакет | Обоснование |
|---|---|---|---|
| Справка о расчётах (xlsx) | `da_*` | `s3-billing` / `ksr-spravki` | генерирует биллинг; **якорь дела** |
| Выписка ЕГРП (pdf) | `dl_*Выписка*` | `s3-docflow` / `ksr-pravoustanav` | система юр. документооборота |
| Платёжное поручение (pdf) | `dl_*Платежное*` | `s3-docflow` / `ksr-pravoustanav` | тот же источник |
| Прочее (pdf) | `50288xxx_*` | `s3-scans` / `ksr-prochee` | смежная система, состав нерегулярен |

**Структура ключей — сохраняем папку должника:** `<ФИО>_<код>/<исходное имя>`. Причины: так пишут реальные источники; `list_objects_v2(Delimiter="/")` даёт список должников через `CommonPrefixes`; при этом КСР **не вычисляется из префикса** — берётся из имени справки, индексатор одинаков для файлового и S3-режимов.

Имена бакетов — только lowercase и дефис: правила S3 запрещают `_` и кириллицу.

### 7.3. Подводные камни заливки

- **NFC/NFD:** macOS отдаёт имена в NFD, Windows/Linux в NFC. Ключ в S3 — просто байты UTF-8, поэтому нормализовать **явно**, иначе один файл зальётся дважды с разных машин
- **`Content-Disposition` с кириллицей** ломает не-ASCII HTTP-заголовок — только `filename*=UTF-8''<percent-encoded>` по RFC 6266
- **`x-amz-meta-*` с кириллицей** → `SignatureDoesNotMatch` или молчаливый мусор; percent-encode
- **`put_object`, а не `upload_file`** в seed — гарантирует single-part, а значит `ETag == MD5` и предсказуемость тестов
- **Лимит ключа 1024 байта UTF-8** — кириллица «съедает» по 2 байта на символ, а имена уже ~120 символов
- **path-style addressing обязателен** — virtual-host стиль для `localhost` не резолвится

### 7.4. Versioning — только на `ksr-pravoustanav`

Даёт тест-кейс «файл заменили» с возможностью достать прежнюю версию. На остальных выключен, чтобы не раздувать том и не ловить delete-marker'ы.

### 7.5. Сценарии тестов

| Сценарий | Как воспроизвести |
|---|---|
| Новый файл | `put_object` нового ключа → скан добавляет документ в дело |
| Замена | `put_object` того же ключа с другим содержимым → новый ETag |
| Удаление | `delete_object` → документ помечается отсутствующим, дело не удаляется |
| Хранилище недоступно | `docker compose stop s3-scans` → остальные индексируются, это со статусом ошибки, **дела не помечаются orphaned** |
| Битые креды | неверный secret → `SignatureDoesNotMatch`, `health=auth_error` |
| Неполное дело | КСР **3455967** — в данных уже так |

### 7.6. Отличия MinIO от AWS

- Нотификации идут в AMQP/Kafka/Redis/webhook, **не** в SNS/SQS/Lambda — код не переносится 1:1
- STS урезанный: `AssumeRole`/`WebIdentity` есть, большинства condition-ключей AWS нет
- Строгая консистентность — но в single-drive dev-режиме versioning ведёт себя иначе, чем в erasure-set
- Нет storage classes, lifecycle в Glacier, части `x-amz-checksum-*`

## 8. Что переносится, меняется, выбрасывается относительно v2.0

| Переносится как есть | Меняется | Выбрасывается |
|---|---|---|
| нормализация КСР, `ksr_pad10` | `rel_path` → `(storage_id, key)` | `file_key`/inode-логика (§3.2) |
| раскладка по слотам, маски | `(size, mtime_ns)` → `(etag, size)` | `mounter.py`, CIFS-монтирование |
| `parser_version`-инвалидация | `Source.path/smb_*` → `Storage.endpoint/bucket/creds` | `share.py`, UNC-резолв |
| журнал `scan_runs` | `os.scandir` → пагинатор `list_objects_v2` | `pending_locked` и фильтр `~$` (§3.6) |
| `is_orphaned`, `is_stale`, `composition_hash` | метаданные → `parsed_docs` по ETag | замер «stat vs парсинг» (в S3 вывод усиливается) |
| APScheduler + кнопка | orphan-фаза условна по health хранилища | режим «одна папка» и `folder.py` |
| модель состояний дела (§5 v2.0) | `printed_at` ставит клиент через API, не сервер | |

**Полностью новое:** аутентификация и роли, presigned-выдача, `file_access_log`, Windows-клиент печати, три MinIO с seed.

## 10. Открытые вопросы

Сведены из четырёх проработок, дубли убраны, сгруппированы по влиянию.

### Блокирующие (меняют модель данных или инфраструктуру)

1. **Сколько реально хранилищ и какие системы-источники?** Три — модель по типам документов. Если в проде два или пять, схему бакетов надо менять до кода.
2. **Какие именно S3** — AWS, MinIO, Ceph RGW, Yandex/VK Cloud? От этого зависят versioning, нотификации, модель консистентности.
3. **Доступен ли S3-endpoint напрямую с клиентских подсетей юрслужбы**, или сеть сегментирована? Решает, нужен ли режим `proxy` (§4.1).
4. **Учётные записи операторов** — заводить в printsys вручную или обязателен вход по доменной учётке AD? Второе — это LDAP-bind как отдельная фаза.
5. **Нужна ли история версий документа для суда?** Если да — versioning везде, и модель становится «документ ↔ версии», а не один объект.
6. **Возврат из суда существует?** (перенесено из v2.0, всё ещё не отвечено) Определяет ветку `RETURNED` и `cycle_no`.

### Важные (меняют эксплуатацию)

7. **Кто и как кладёт файлы в S3 в проде** — сама система-источник, ETL, оператор вручную? Определяет, можно ли рассчитывать на стабильность ключа.
8. **Гарантируется ли, что все документы дела лежат в одном пространстве имён** (папка должника)? Если ЕГРП кладётся плоско, связка идёт только через КСР в имени — подтвердить, что он там всегда есть.
9. **Может ли источник перезаливать файл без изменения содержимого** (ночной батч «всё заново»)? Тогда ETag не меняется — это плюс, но подтверждает решение не включать `LastModified` в триггер.
10. **Принтеры расшарены с сервера печати AD или подключены напрямую?** Влияет на диагностику, спроектировать надо сейчас.
11. **Модели принтеров и число лотков одинаковые на всех местах?** Если зоопарк — конфиг лотков должен быть на принтер, а не глобальный.
12. **Кто физически подтверждает «стопка принята»** — по каждому делу или один чек на пакет? На 1000 делах это разный объём ручной работы.
13. **Требование СБ/152-ФЗ** на срок хранения аудита доступа к ПДн и шифрование локального кеша — 3 года и DPAPI достаточно?
14. **Кто играет роль `admin`** (правит доступы к S3) — оператор юрслужбы или ИТ?

### Уточняющие

15. **Реальный масштаб:** сколько объектов в каждом бакете сегодня и через год, сколько новых в сутки? На 20k полный скан бесплатен, на 2M — пересматривать интервал.
16. **Допустима ли задержка появления дела до 10 минут** или нужен «почти realtime»?
17. **Разрешена ли установка стороннего PDF-принтера** (Bullzip) на тестовую машину — политики домена могут блокировать драйверы печати.
18. **Есть ли Windows-агент для CI** (self-hosted runner с реальным спулером), или интеграционные тесты печати гоняем вручную?
19. **Допустимо ли, что presigned-ссылку может использовать любой, кто перехватит её в течение 15 минут**, или СБ требует одноразовость (тогда только proxy-режим)?

### Отвечено ранее

- Папка/хранилище настраивается администратором, оператор свои источники не добавляет
- Microsoft Excel установлен у всех операторов (корпоративный Office)
- Сканер один на систему, а не по клиенту на оператора
- Печать выполняет клиент, не сервер
