# Спецификация: Система печати судебных дел

**Версия:** 2.0 · **Дата:** 2026-09-02 · **Статус:** архитектура зафиксирована, часть вопросов открыта

История версий:
- **1.0** — HTML-прототип (client-side, File System Access API). Реализован, `printsys.html`.
- **1.5** — серверное веб-приложение (FastAPI + HTMX + PG + Docker). Реализовано, ветка `main`.
- **2.0** *(этот документ)* — серверный сканер + Windows-клиент печати. Основание: три экспертных проработки от 2026-09-02 и последующая правка заказчика (сканер должен быть один, а не по клиенту на каждого оператора).

---

## 1. Context

Оператор юридической службы готовит пакеты документов для подачи в суд по долгам ЖКУ. Внешняя система (биллинг) выгружает документы в **общую сетевую папку**. Оператор должен увидеть новые дела, проверить комплектность, распечатать пакет в строго заданном порядке (для сшивания), отметить факт печати и факт передачи в суд.

Единица работы — **дело**, ключ = код КСР.

### Почему архитектура меняется

Версия 1.5 (сервер в Docker сканирует смонтированную папку, браузер печатает) уперлась в три стены:

1. **Печать.** Браузер не даёт массовую тихую печать на выбранный принтер — Chromium 10+ лет закрывает такие запросы как WONTFIX. Диалог на каждое дело либо один гигантский PDF на пакет — оба варианта неприемлемы на объёмах 100–1000 дел.
2. **Двойной сетевой пробег.** Файлы лежат на шаре, которую видит и клиент, и сервер. Сервер читал их и отдавал клиенту по HTTP — те же байты ходили по сети дважды.
3. **Хрупкость конвертации.** LibreOffice в контейнере даёт приемлемую, но не идентичную Excel вёрстку; `openpyxl` падает на части реальных файлов биллинга.

**Что переносится на клиента:** чтение документов при печати, конвертация через Excel COM, сама печать. Это закрывает все три проблемы.

**Что остаётся на сервере:** сканирование и индексация. Папка и база дел общие — значит сканер должен быть один, иначе гонки и расхождения (§3.1).

### Проверено живьём (2026-09-02, эта машина)

| Механизм | Результат |
|---|---|
| Excel COM → PDF | 2.9 сек, вёрстка 1-в-1 с Excel |
| `win32print` DEVMODE | Читается и меняется `Copies`, `Duplex`, `DefaultSource` (лоток) — per-job настройки работают |
| `python-calamine` | Прочитал 7/7 файлов заказчика, где `openpyxl` падал с `TypeError` в `parse_col_breaks` |

## 2. Целевая архитектура

```
                    ┌───────────────────────┐
                    │  Сетевая шара (SMB)   │
                    │  общая для всех       │
                    └───┬───────────────┬───┘
       CIFS read-only,  │               │  UNC, под учёткой
       сервисная УЗ     │               │  оператора
                        ▼               │
┌─ Сервер (FastAPI + PostgreSQL) ────┐  │
│                                     │  │
│  СКАНЕР (единственный экземпляр)    │  │
│  • обход каждые 5–10 мин            │  │
│  • парсинг xlsx (calamine)          │  │
│  • инкрементальный кеш              │  │
│  • единственный writer в реестр     │  │
│                                     │  │
│  РЕЕСТР                             │  │
│  • дела, статусы, история, аудит    │  │
│  • настройки (слоты, лейблы)        │  │
│  • локи печати — арбитр             │  │
│  • артефакты печати (PDF)           │  │
│  • дашборд руководителя             │  │
└──────────────┬──────────────────────┘  │
               │ HTTPS: source_id +      │
               │ rel_path, статусы       │
               ▼                          │
┌─ Клиент (Windows, у оператора) ────────┴──┐
│ • получает СПИСОК ПУТЕЙ, не файлы          │
│ • резолвит root_unc + rel_path             │
│ • читает документы с шары НАПРЯМУЮ ────────┘
│ • Excel COM → PDF (вёрстка 1-в-1)
│ • сборка дела, подвал КСР/NN
│ • печать win32print + DEVMODE
│ • UI — HTMX от локального FastAPI
└────────────────────────────────────────────┘
```

Три свойства, которые даёт такое разделение:

- **Один сканер** → нет гонок, нет расхождений, база свежая независимо от того, кто в сети
- **Файлы не ходят через сервер** → клиент читает с шары напрямую, нет двойного сетевого пробега
- **Аудит сохранён** → документы читаются под учёткой оператора в момент печати

## 3. Зафиксированные архитектурные решения

### 3.1. Разделение ответственности: сканирует сервер, печатает клиент

**База дел общая, папка общая — значит сканер должен быть один.**

| Операция | Где | Почему |
|---|---|---|
| **Сканирование и индексация** | Сервер (CIFS read-only, сервисная УЗ) | Единственный writer в реестр → нет гонок; один обход на всех; работает 24/7 |
| **Чтение документов при печати** | Клиент, напрямую с шары под учёткой оператора | Файлы не ходят через сервер; аудит «кто работал с делом» сохраняется |
| **Конвертация и сборка PDF** | Клиент (Excel COM) | Вёрстка 1-в-1, серверу LibreOffice не нужен |
| **Печать** | Клиент (`win32print`) | Per-job DEVMODE: лоток, дуплекс, копии |

Сервер отдаёт клиенту **список путей** (`source_id` + `rel_path`), клиент резолвит `root_unc + rel_path` и читает документы сам.

#### Почему НЕ «каждый клиент сканирует сам»

Этот вариант рассматривался и **отвергнут** — при общей папке и общей базе он даёт шесть режимов отказа:

1. **N-кратная избыточная работа** — пять операторов обходят одно дерево ради одного результата
2. **Гонка манифестов** — два клиента отсканировали, последний перезаписывает; аренда смягчает, но не устраняет (упавший клиент держит аренду до TTL, «Форсировать» открывает гонку заново)
3. **Расхождение из-за прав NTFS** — клиент А видит 100 файлов, клиент Б 80; манифест Б «удалит» 20 файлов из общего реестра
4. **Расхождение из-за блокировок** — у А справка открыта в Excel (`pending_locked`), у Б в тот же момент читается нормально
5. **База обновляется только пока кто-то работает** — ночная выгрузка биллинга повиснет до утра
6. **Разные версии клиента** — `parser_version` 3 и 4 гоняют перепарсинг туда-обратно

#### Про аргумент аудита

Первоначальная проработка защищала клиентское сканирование аудитом. Аргумент **смешивал две разные операции**:

- **Сканирование** — перечисление файлов и чтение шапки xlsx. Это индексация, пофамильный аудит не нужен
- **Печать** — чтение документов целиком и вывод на бумагу. Вот здесь аудит критичен — и печать в любом случае остаётся на клиенте под учёткой оператора

Аудит «кто работал с делом должника» сохраняется полностью при серверном сканировании.

#### Условие развёртывания

Сканер должен физически дотягиваться до шары. **Подтверждено заказчиком: сервер в той же сети и видит шару** → сканер живёт в серверном контейнере.

Если бы не видел — тот же код разворачивался бы отдельной службой Windows на машине, которая видит, и ходил к серверу по HTTPS. Код один, различается только деплой.

### 3.2. Личные папки — исключение из правила «сканирует сервер»

Personal-источник (см. §3.3) сервер по определению не видит — он локален для машины оператора. Такие источники сканирует **клиент**, и это не создаёт гонок: у personal-источника ровно один сканер по построению (`owner_user_id` + `machine_id`).

### 3.3. Личные папки клиента — разрешены, но отдельным классом

`Source.kind ∈ {shared, personal}`.

- **shared** — общая сетевая шара, видна всем, синхронизируется полностью
- **personal** — локальная папка оператора (донесённые вручную сканы, черновики, «Загрузки»), привязана к `owner_user_id` + `machine_id`, видна только владельцу

На сервер из personal-источника уходят **только метаданные** (КСР, слот, имя файла, размер), содержимое остаётся локально. Дело, где хотя бы один файл из personal, помечается `is_local_only=true`, в отчётах руководителю попадает отдельной строкой, при отметке «передано в суд» показывается предупреждение.

Логика запрета обратная: если личные папки запретить, оператор начнёт копировать черновики в общую шару — станет хуже.

### 3.4. Триггеры сканирования

Сканер один (серверный), поэтому аренда и разрешение гонок не нужны. Три триггера, дополняющих друг друга:

| Триггер | Задержка | Назначение |
|---|---|---|
| **Таймер каждые 5–10 мин** | до 10 мин | база, работает всегда |
| **Маркер-файл от биллинга** | секунды | если выгрузка кладёт `_batch_YYYYMMDD.done` — сканер проверяет наличие одним листингом и сканирует сразу |
| **Кнопка «Сканировать сейчас»** | немедленно | когда файл донесли руками |

Маркер-файл требует кооперации биллинга — вынесено в открытые вопросы §14.

### 3.5. Сканирование, а не мониторинг

**Файловые watcher'ы по SMB не дают гарантий:**

- `ReadDirectoryChangesW` через редиректор ограничен буфером 64 КБ; при переполнении молча выбрасывает весь буфер (`ERROR_NOTIFY_ENUM_DIR` — «перечисли каталог сам»)
- `SMB2 CHANGE_NOTIFY` — one-shot запрос; между ответом и переподпиской есть окно, события в нём теряются безвозвратно
- `inotify` на CIFS-монтировании **не работает вообще** — не видит изменений, сделанных другими клиентами
- `watchdog` на сетевом пути обязан использовать `PollingObserver`, который сам падает при обрыве сети, часто тихо

Любой watcher всё равно требует полного перечисления как fallback — значит это **оптимизация задержки, а не архитектура**.

### 3.6. Экономия: кешировать парсинг, а не экономить на обходе

**Замеры (2026-09-02, локальный диск, реальные файлы заказчика):**

| Операция | Время | Отношение |
|---|---|---|
| `stat` одного файла | 31 мкс | 1× |
| Парсинг справки (calamine) | 1.5 мс | **47×** |

Прогноз на 5 000 справок / 20 000 файлов за цикл по SMB:

| Что | Время |
|---|---|
| Обход дерева (`os.scandir`, метаданные пачками) | 5–15 с |
| **+ парсинг всех справок заново** | **+60–100 с** ← дорого |
| + парсинг только изменившихся | ≈0 с |

**Вывод: обход не является узким местом.** 5–15 секунд раз в 10 минут приемлемо. Дорого перечитывать и парсить справки — значит кешировать надо парсинг.

**Четыре слоя кеширования:**

1. **Обход** — полностью каждый цикл, `os.scandir` рекурсивно. Дёшево и **гарантированно ничего не теряет**
2. **Парсинг справки** — ключ `(rel_path, size, mtime, parser_version)`; совпал → пропускаем. Выигрыш 5–10× на цикле
3. **Сборка PDF** — ключ `composition_hash`; пересобираем только при изменении состава дела
4. **Ночная полная сверка** — читаем `size+mtime` всех файлов; ловит изменение содержимого на месте

#### Отвергнуто: пруннинг по mtime каталога

Идея — не заходить в папки, чей mtime не изменился. **Проверено экспериментально (2026-09-02):**

| Событие | Меняется mtime каталога |
|---|---|
| Добавлен файл | да, у самой папки |
| Удалён файл | да, у самой папки |
| Переименован файл | да, у самой папки |
| Создана подпапка | да, у родителя |
| **Изменено содержимое файла на месте** | **нет ни у кого** |

mtime **не распространяется вверх по дереву** — изменение в `Доки2/Должник_2/` не меняет mtime `Доки2/`.

Главное: `os.scandir` отдаёт **устаревший** mtime подпапок (метаданные из записи каталога обновляются лениво) — в тесте **100 промахов из 100** сразу после изменения, догоняет через ~0.5 с. На SMB кеширование агрессивнее и зависит от файлового сервера.

Выигрыш пруннинга — те самые 5–15 секунд, которые и так не мешают. Цена ошибки — **дело тихо не появится в реестре, и оператор его не напечатает**. Размен неприемлем.

Вернуться к пруннингу — если объёмы вырастут до сотен тысяч файлов, и только с ночной полной сверкой как гарантией.

### 3.5-bis. Подключение шары и двойное представление пути

Сервер и клиент видят одну папку по-разному, поэтому у источника **два пути**:

| Поле | Кто использует | Пример |
|---|---|---|
| `path` | сервер (сканер) | `/data/share` |
| `root_unc` | клиент (чтение при печати) | `\\srv-docs\ksr` |

Файл хранится как `rel_path` относительно корня. Сервер читает `path + rel_path`,
клиенту отдаётся `root_unc + rel_path` (обратные слеши, защита от `..`).

**Без `root_unc` клиент печатать не сможет** — в UI источник помечается явно,
а в API-ответе поле `files_unresolved` считает такие файлы.

**Монтирование** — два поддерживаемых способа (детали в `docs/deployment.md`):
- **на хосте** через `fstab` с `_netdev,x-systemd.automount` и bind-mount в контейнер (рекомендуется: хост сам переподключается)
- **средствами Docker** через том с `driver_opts: type=cifs` (привилегированный контейнер не нужен, но переподключение после долгого обрыва хуже)

**Проверка доступности.** Стухший CIFS-mount коварен: `exists()` может вернуть
`True`, а первое чтение упасть с `ESTALE`/`EIO`. Поэтому здоровье источника
проверяется реальным чтением каталога (`GET /api/health`), состояния:
`ok` · `empty` · `missing` · `denied` · `stale`.

**Поведение при обрыве связи:** скан источника падает с ошибкой, остальные
источники сканируются нормально, **дела недоступного источника не помечаются
потерянными** — пометка `orphaned` возможна только после успешного обхода.
Иначе обрыв сети разом «потерял» бы весь реестр.

### 3.6. Модель путей

**UNC не является первичным ключом.** Первичный ключ дела — `(source_id, ksr)`; путь это атрибут файла, а не идентичность.

Три уровня хранения: `source_id` → `rel_path` (от корня источника) → `file_name`. Полный путь собирается как `source.root_unc + rel_path`. Переезд шары = смена одного поля `root_unc`.

Дополнительно:
- Клиент резолвит подключённые буквы в UNC через `win32wnet.WNetGetConnection('Z:')`
- **DFS-пути не резолвим** — DFS сам абстрагирует переезд
- `file_id` (128-бит) + `volume_serial` из `GetFileInformationByHandleEx` — **инвариант при переименовании/перемещении**. Критично: у заказчика подпапки названы по ФИО должника и переименовываются
- Нормализация: lowercase для сравнения, NFC для кириллицы, `\\?\UNC\` только внутри API-вызовов, не в БД

### 3.7. Разные права на подпапки — состояние, а не ошибка

Клиент при сканировании фиксирует `access_denied` по конкретному каталогу и отправляет на сервер как `visibility_gap`, **а не молча пропускает**. Дело, чьи файлы частично недоступны текущему оператору, показывается со статусом «неполный комплект — нет доступа», печать блокируется.

Реестр дел общий (метаданные видны всем), доступ к содержимому — по NTFS.

## 4. Модель данных

### 4.1. Источники и файлы

```
sources
  id, name, kind (shared|personal), root_unc,
  owner_user_id NULL, machine_id NULL,      -- только для personal
  is_readonly bool default true,
  scan_recursive bool, include_globs, exclude_globs,
  last_scan_at, last_scan_status, enabled,
  created_by, created_at

source_file                                  -- инкрементальный кеш сканера (на сервере)
  source_id, rel_path (ключ), name, ext,
  size, mtime_utc,
  file_id, volume_serial,                    -- инвариант при переименовании
  content_hash,                              -- blake2b, лениво: только справки
  ksr, parsed_meta_json, parser_version,     -- кеш парсинга
  last_seen_scan_id, state (ok|pending_locked|denied|missing)

source_access_gaps
  id, source_id, user_id, machine_id, rel_path, seen_at
```

### 4.2. Дела

```
cases
  source_id, ksr                             -- составной первичный ключ
  date_formed, account, period, provider, service
  slots_json                                 -- {slot_id: [{name, rel_path, file_id, hash}]}
  fileset_version                            -- хэш набора файлов; растёт при любом изменении
  composition_hash                           -- хэш [(file_id, slot, order, hash)]
  status                                     -- см. §5
  cycle_no                                   -- номер цикла подачи (возврат из суда)
  assignee_id, claimed_at                    -- мягкий claim
  is_local_only                              -- есть файлы из personal-источника
  is_stale, is_orphaned                      -- ортогональные флаги
  printed_at, submitted_at, archived_at
  first_seen_at, updated_at
```

**Комплектность не хранится** — это вычисляемая проекция файлов, пересчитывается при каждом скане.

### 4.3. Печать и аудит

```
print_jobs
  id, created_by, created_at, printer_name, tray, duplex, copies,
  status (QUEUED|RUNNING|PAUSED|COMPLETED|PARTIAL|CANCELLED),
  total_cases, done_cases, failed_cases

print_job_items
  job_id, ksr, order_no,
  status (PENDING|SENT|DONE|FAILED),
  pages, error_code, started_at, finished_at

print_history                                -- по факту печати
  case_id, print_job_id, ts, actor, printer_name, tray, duplex, copies,
  pages_total, pages_per_slot,
  fileset_version, files_snapshot,           -- доказательство состава
  pdf_artifact_id,
  result, error_code,
  reason (first|reprint_jam|reprint_stale|recycle)

event_log                                    -- append-only, ничего не удаляется
  id, ts, case_id, cycle_no, actor_id, actor_host,
  event_type, from_status, to_status, payload_json, print_job_id
```

**Собранный PDF хранится на сервере как артефакт печати** — иначе невозможно доказать, что именно печаталось.

## 5. Модель состояний дела

```
        [файлы появились в папке]
              │ скан находит якорь (Справка), КСР извлечён          [АВТО]
              ▼
        ┌───────────┐  «не наше» / мусор            ┌──────────┐
        │   NEW     │──────────────────────────────►│ EXCLUDED │
        │ (в работе)│◄──────────────────────────────└──────────┘
        └───────────┘             вернуть
              │ «взять в работу» / назначение                [РУЧН.]
              ▼
        ┌───────────┐  снять / таймаут 24 ч         [АВТО]
        │  CLAIMED  │──────────────────────────────► NEW
        └───────────┘
              │ старт печати (проверка комплектности) [РУЧН. подтверждение]
              ▼
        ┌───────────┐   сбой / отмена     ┌──────────────┐
        │ PRINTING  │────────────────────►│ PRINT_FAILED │──► повтор ──► PRINTING
        └───────────┘                     └──────────────┘
              │ job завершён успешно                    [АВТО от клиента]
              ▼
        ┌───────────┐  fileset_version изменился  [АВТО, флаг STALE]
        │  PRINTED  │──────────────────────────────► PRINTED+STALE
        └───────────┘                                      │ перепечать
              │ «передано в суд»              [РУЧН.]      └──► PRINTING
              ▼
        ┌───────────┐   возврат / брак   [РУЧН.]  ┌──────────┐
        │ SUBMITTED │────────────────────────────►│ RETURNED │──► NEW (cycle_no+1)
        └───────────┘                             └──────────┘
              │ +N дней или «закрыть»          [АВТО/РУЧН.]
              ▼
        ┌───────────┐
        │ ARCHIVED  │   скрыто из рабочего списка, данные живы
        └───────────┘

Ортогонально, из любого состояния:
  файлы исчезли из папки → флаг ORPHANED (запись остаётся; в NEW через 30 дней → EXCLUDED)
```

### Таблица переходов

| Переход | Кто | Авто? | Что записывается |
|---|---|---|---|
| → NEW | сканер клиента | да | КСР, метаданные, файлы+слоты, `fileset_version`, `first_seen_at` |
| NEW → CLAIMED | оператор / руководитель | ручн. | `assignee_id`, `claimed_at` |
| CLAIMED → NEW | таймаут 24 ч / снятие | авто+ручн. | `released_at`, причина |
| → PRINTING | оператор (подтверждение) | ручн. старт | `print_job_id`, снапшот состава и хэшей |
| PRINTING → PRINTED | клиент по коду возврата `win32print` | да | `printed_at`, листов, принтер, лоток, длительность |
| PRINTING → PRINT_FAILED | клиент / оператор | да | код ошибки, № дела в пакете, «докуда дошло» |
| PRINTED → SUBMITTED | оператор | ручн. | `submitted_at`, кем, № реестра подачи |
| SUBMITTED → RETURNED | оператор | ручн. | причина (enum: неверный документ / определение суда / прочее) |
| RETURNED → NEW | оператор | ручн. | `cycle_no += 1`, прошлая печать остаётся в истории |
| → ARCHIVED | через N дней после SUBMITTED | авто | `archived_at` |
| любой → +STALE | сканер при смене `fileset_version` после печати | да | diff: что добавлено/заменено/удалено |
| любой → +ORPHANED | сканер | да | `files_missing_since` |

## 6. Инкрементальное сканирование

**«Изменилось»** = `(size, mtime_utc)` отличается **или** `parser_version` вырос.
**Переименование** = тот же `file_id`, другой `rel_path` → не перепарсиваем, только переразложение по слотам.
**Удаление** = `last_seen_scan_id < current_scan_id`.
**Дело пересобирать**, если изменился `composition_hash` = хэш `[(file_id, slot, order, content_hash)]`. При расхождении сбрасывается кеш PDF, `printed_at` **сохраняется**, ставится флаг STALE.

```
scan_id = open_scan(source_id)
for f in scandir_recursive(root):         # os.scandir: метаданные приходят пачками
    if f.name.startswith("~$"): continue  # lock-файлы Excel
    row = cache.get(f.rel_path)
    if row and row.size == f.size and row.mtime == f.mtime and row.pv == PARSER_V:
        cache.touch(f.rel_path, scan_id); continue        # СЛОЙ 2: парсинг пропущен
    if row is None and (row := cache.by_file_id(f.file_id)):
        cache.rename(row, f.rel_path, scan_id); continue  # переименование, не перепарсиваем
    meta = parse_spravka(f) if is_spravka(f) else None     # дорого — только для новых/изменённых
    cache.upsert(f, meta, scan_id)
missing = cache.not_seen(scan_id)
commit_scan(scan_id, build_cases(cache.all(scan_id), slots), missing)   # одна транзакция
```

**Идемпотентность.** Кеш коммитится по файлам, `commit_scan` — одной транзакцией. При обрыве повтор пропускает файлы с текущим `scan_id`; «удалённые» не фиксируются, пока скан не завершён — иначе оборванный обход «сотрёт» полдерева.

**Сканер один**, поэтому аренды и разрешения конфликтов не требуется. Достаточно одиночного запуска (advisory lock в PG или флаг «скан идёт») — чтобы таймер не наложился на ручной запуск.

### 6.1. Что различает каждый скан

Три категории изменений, фиксируются в журнале `scan_runs` и показываются оператору после скана:

| Категория | Как определяется | Что происходит |
|---|---|---|
| **Новые** | `rel_path` отсутствует в кеше и `file_id` не найден | Файл парсится (если справка), раскладывается по слотам. Новая справка → новое дело |
| **Изменённые** | `(size, mtime)` отличается от кеша, либо вырос `parser_version` | Перепарсивается. Если это меняет `composition_hash` дела — сбрасывается кеш PDF; для уже напечатанного дела ставится флаг `STALE` |
| **Переименованные** | `rel_path` новый, но `file_id` совпал с существующей записью | **Не перепарсивается** — только обновляется путь и переразложение по слотам |
| **Пропавшие** | `last_seen_scan_id < текущий scan_id` | Помечается `state=missing`. Дело не удаляется: если пропали все файлы — флаг `ORPHANED`; если часть — слот показывается пустым, комплектность пересчитывается |
| **Заблокированные** | Ошибка доступа при чтении (открыт в Excel) | `state=pending_locked` после 3 ретраев. **Не считается пропавшим**, показывается отдельно в diff-панели |

**Пропавшие файлы никогда не удаляют дело.** Запись остаётся с флагом, потому что факт печати и передачи в суд — юридически значимая история, которую нельзя стирать исчезновением файла на шаре.

Журнал `scan_runs`: `id, source_id, started_at, finished_at, status, files_seen, files_new, files_changed, files_renamed, files_missing, files_locked, cases_new, cases_updated, cases_orphaned, duration_ms, error`.

## 6.2. Что живёт в серверном контейнере

Раз сборка PDF и печать уехали на клиента, серверу **не нужны**: LibreOffice, шрифты для рендеринга, `reportlab`, `pypdf`. Образ ужимается с ~1.2 ГБ обратно до ~250 МБ.

Серверу нужны:

| Компонент | Зачем |
|---|---|
| FastAPI + uvicorn + Jinja2 | REST API для клиента + веб-дашборд |
| SQLAlchemy + asyncpg + Alembic | реестр в PostgreSQL |
| **python-calamine** | парсинг метаданных справки (основной) |
| openpyxl | резервный парсер |
| APScheduler | таймер периодического скана |
| pydantic / pydantic-settings | конфигурация и схемы |

Клиенту (отдельный дистрибутив, не контейнер) нужны: `pywin32` (печать, UNC-резолв), Excel COM (конвертация), `pypdf` (склейка), `reportlab` (титульный лист и подвал).

**Файл занят Excel** — 3 ретрая с backoff, затем `pending_locked`: **не считать удалённым**, показать в diff-панели.

## 7. Извлечение КСР и раскладка по слотам

Правила не меняются относительно v1.5:

- **Якорь дела** — файл с подстрокой `Справка о расчетах по ЖКУ` и расширением `.xlsx`/`.xls`
- **КСР** = первое число в имени якоря, `ltrim('0')`. Пример: `da_0003455945_Справка...xlsx` → `3455945`
- **Прочие файлы** цепляются, если содержат КСР в имени в любой форме: `3455945` или `0003455945`
- **Слоты** — настраиваемый список `{название, маска (подстрока или /regex/), обязательный?, порядок}`. Файл попадает в первый подходящий слот; не подошедшее — в catch-all «Прочее»
- **Порядок слотов = порядок листов в PDF** (критично для сшивания)

**Парсинг справки:** основной ридер — `python-calamine` (Rust, устойчив), резервный — `openpyxl`. Значение лейбла ищется **сканированием вправо до первой непустой ячейки** (до 6 колонок) — в реальных файлах лейбл в A, значение в C, между ними merged-ячейки. Лейблы нормализуются с удалением `№`.

## 8. Многопользовательская работа

Сервер — единственный арбитр: через общую папку координироваться невозможно.

**Два уровня, намеренно разные по жёсткости:**

- **Мягкий claim** (advisory) — «взять в работу», бейдж «У Иванова», таймаут 24 ч, снимается кем угодно с записью в аудит. Информирует, не блокирует.
- **Жёсткий лок только на время печати** (обязательный) — атомарный захват при формировании `print_job`: `UPDATE ... WHERE status <> 'PRINTING'`. Второй оператор физически не стартует печать того же дела; пакет покажет «3 дела пропущены, печатаются Петровым».

Обоснование асимметрии: жёсткий лок на весь цикл парализует работу при отпусках и забытых claim; мягкий без жёсткого не защищает от двойной печати бумаги. **Двойная печать — единственный реально дорогой конфликт, только он и запирается.**

**Распределение работы:** вручную (взять/назначить) + сохранённые фильтры-«очереди» (по поставщику / услуге / диапазону дат) как рабочие зоны. Автораспределение round-robin на старте не вводим — объёмы малы, прозрачность важнее.

## 9. Печать пакета

1. Выбор дел → сервер валидирует: комплектность, чужие локи, STALE
2. **Экран подтверждения**: N дел, ~M листов, принтер / лоток / дуплекс / копии, список исключённых с причинами
3. Создаётся `print_job` (QUEUED) с позициями; дела → PRINTING (лок)
4. Клиент собирает PDF по одному (Excel COM → PDF → склейка → титул → подвал) и шлёт в `win32print` **отдельным job на дело** — принципиально: один job = одно дело = атомарная единица отката
5. Прогресс «17 из 60, текущее КСР 123456», кнопки **Пауза / Стоп**. Каждая позиция репортится на сервер сразу — при падении клиента состояние не теряется
6. **Сбой** (зажевало / кончилась бумага): Стоп → job PAUSED. Позиции: DONE / FAILED / PENDING. Кнопка **«Продолжить с места обрыва»** печатает только PENDING+FAILED; дела в DONE повторно не идут
7. **Спорная позиция** («ушло в принтер, но не вышло») — статус SENT, оператор подтверждает вручную. Система не знает физику принтера — здесь решает человек
8. Завершение → COMPLETED / PARTIAL, локи снимаются, сводка «58 ок, 2 требуют повтора»

## 10. Развилки и исключения

| Ситуация | Решение |
|---|---|
| **Файлы приходят порознь** (справка есть, ЕГРП завтра) | Дело создаётся сразу по якорю, живёт в NEW «неполное: не хватает ЕГРП». Печать — только через явное подтверждение «Печатать без ЕГРП», флаг и причина в аудит |
| **Дубликаты в слоте** (два платёжных поручения) | Слот — список. По умолчанию печатаются **все**, сортировка по mtime, в описи «Платёжное поручение (2 док.)». Если слот `single=true` — берётся свежий, дело подсвечивается «требует выбора». Тихо брать последний **запрещено** |
| **Файл заменили после печати** | `fileset_version` изменился → флаг **STALE** + diff. Дело в отдельном фильтре «требует перепечати». `printed_at` не стирается — он относится к прошлой версии |
| **Замялся лист** | Оператор открывает job → «перепечатать дело N» или «страницы X–Y дела N» (PDF закэширован). Новая запись `print_history` с `reason=reprint_jam`, `printed_at` не меняется |
| **Передали в суд, документ неверный** | SUBMITTED → RETURNED с причиной → NEW, `cycle_no=2`. История циклов сохраняется — юридически значимо |
| **Файлы удалили из папки** | Запись остаётся, флаг ORPHANED. Собранный PDF хранится на сервере как доказательство состава |
| **Оператор в отпуске** | Таймаут claim 24 ч → авто-освобождение. Дашборд «зависшие»: CLAIMED > 1 дня, PRINTED без SUBMITTED > 3 дней, PRINT_FAILED без повтора |
| **Оператор не видит части подпапок** | `visibility_gap` → дело «неполный комплект — нет доступа», печать заблокирована, а не тихий недокомплект |
| **Шара недоступна** | Клиент работает офлайн по кешу метаданных, печать блокируется с явным сообщением |
| **Excel COM завис** | Дело → «ошибка конвертации», ретрай; остальные дела не блокируются |

## 11. Автомат vs человек

**Полностью автоматически:** обнаружение дел, извлечение КСР и метаданных, раскладка по слотам, расчёт комплектности, `fileset_version` / STALE / ORPHANED, `printed_at`, сборка PDF и нумерация, таймаут claim, архивация, весь аудит.

**Обязательно человек:** печать неполного дела (с причиной); выбор файла при дубле в `single`-слоте; **`submitted_at`** — система не знает, что бумаги физически ушли; подтверждение спорной позиции печати; возврат из суда и его причина; исключение дела как «не наше»; снятие статусов; переназначение чужой работы; старт любого пакета печати.

## 12. Безопасность и аудит

- **Только доменные учётки операторов.** Сервисная УЗ не нужна — CIFS-mount на сервере отвергнут
- **Шара read-only** на уровне NTFS для группы `PRINTSYS-Operators`. Собранный PDF пишется в отдельный каталог или локальный temp — приложение не должно иметь возможности испортить исходники
- **Аудит чтения файлов** — штатный Windows File Server Auditing (Object Access, событие 4663). В приложении — только бизнес-аудит (`event_log`)
- **Транспорт** — TLS; аутентификация клиента доменная

**Отчёты руководителю:** воронка по статусам за период; продуктивность по операторам; зависшие дела; исключения (печать без обязательных слотов, снятые статусы, снятия чужих claim); расход бумаги по принтерам; возвраты из суда с причинами; SLA «от появления файлов до подачи».

## 13. Найденные дефекты текущей реализации

| Дефект | Статус |
|---|---|
| `openpyxl` падает с `TypeError` в `parse_col_breaks` на реальных файлах биллинга; исключение глушилось, метаданные пустые | **Исправлено** (коммит `4210fc8`): основной ридер `python-calamine`, `openpyxl` резервный |
| Значение лейбла искалось только в соседней ячейке `c+1`, а лежит в `C` (merged-ячейки) | **Исправлено** (`4210fc8`): скан вправо до первой непустой |
| «Удалить дело» сбрасывает статусы; при следующем скане дело возвращается чистым — **скрытый способ стереть факт печати** | **Открыто.** Заменить на `EXCLUDED` (мягкое исключение с сохранением истории); физическое удаление — только админу |
| Порядок роутов: `/{ksr}/pdf` перехватывал `/batch/pdf` | Исправлено (`937ea8b`) |
| `Content-Disposition` с кириллицей → `UnicodeEncodeError` | Исправлено (`937ea8b`): ASCII + `filename*` по RFC 5987 |

## 14. Открытые вопросы к заказчику

Сгруппированы по тому, насколько сильно ответ меняет реализацию.

### Блокирующие (меняют модель данных)

1. **Возврат из суда существует?** Если дело после подачи может вернуться и подаваться повторно — нужны `cycle_no` и вся ветка RETURNED. Если нет — модель упрощается примерно на треть.
2. **Есть ли реестр/номер подачи в суд** (пачка дел одной датой, сопроводительное письмо)? Если да — нужна отдельная сущность «подача», `submitted_at` становится её атрибутом, появляется массовая операция «сформировать реестр».
3. **Дубликат в слоте — норма или ошибка данных?** Два платёжных поручения на один КСР — «печатать оба» или «биллинг накосячил, нужен алерт»?
4. **Роль «руководитель» нужна отдельно** или все операторы равноправны и видят всё? Решает, вводить ли RBAC сейчас.

### Важные (меняют инфраструктуру)

5. **Есть ли DFS-namespace** или планируется? Если да — канонизируем на DFS-путь, вопрос переезда шары закрывается инфраструктурно.
6. **Есть ли сервисная учётная запись** для монтирования шары на сервер (read-only), или её нужно заводить?
7. **Может ли биллинг класть маркер-файл** (`_batch_YYYYMMDD.done`) по завершении выгрузки? Это даёт «почти мгновенное» появление дел вместо ожидания до 10 минут — дёшево, но требует кооперации смежной системы.
8. **Куда писать готовый PDF** — обратно в шару, в отдельный выходной каталог, или не сохранять вовсе?
9. **Срок хранения** аудита и собранных PDF — что требует юрслужба формально? (Предложение: `event_log` и `print_history` — 3 года по исковой давности; PDF-артефакты — 6–12 мес, дальше только метаданные и хэш.)
10. **Разрешено ли операторам использовать локальные папки**, или ИБ требует работу исключительно из шары?

### Уточняющие (влияют на настройки, не на архитектуру)

11. **Допустима ли задержка появления нового дела до 10 минут**, или нужен «почти realtime» (см. вопрос 7 про маркер-файл)?
12. **Могут ли файлы изменяться на месте** (перезалив справки с тем же именем), или только добавляться? От этого зависит, нужна ли ночная полная сверка или достаточно дневных циклов.
13. **Кто и когда чистит старые дела на шаре** — есть ли архивация, при которой массовое исчезновение файлов нормально?
14. **Ожидаемый размер дерева через год** (файлов, не дел) — определяет, останется ли полный обход за цикл приемлемым (при 20 000 файлов — 5–15 с, запас большой).
15. **Два оператора могут легитимно печатать одно дело** (например, копия в дело)? От этого зависит, лок это или предупреждение.
16. **Что делать со STALE-делом, уже переданным в суд** — молча игнорировать замену файла или заводить инцидент?

- **Сервер в той же сети и видит шару** → сканер разворачивается в серверном контейнере
- **Microsoft Excel установлен у всех** операторов (корпоративный Office) → конвертация через Excel COM
- Веб-интерфейс на сервере — решение о его судьбе отложено до прототипа

## 15. План реализации

| Веха | Содержание | Оценка |
|---|---|---|
| **1. Серверный сканер** | CIFS-монтирование шары read-only; инкрементальный кеш `source_file` (`file_id`, `size`, `mtime`, `parser_version`); обработка переименований и `pending_locked`; таймер 5–10 мин + кнопка; `composition_hash` | 3–4 дня |
| **2. Клиент печати** | Точка входа `printsys-desktop`; локальный FastAPI на 127.0.0.1; получение списка путей от сервера; резолв `root_unc + rel_path`; чтение с шары напрямую; Excel COM → PDF; сборка дела с подвалом; `win32print` + DEVMODE (принтер, лоток, дуплекс, копии) | 4–5 дней |
| **3. Модель состояний** | Переход с `printed_at`/`submitted_at` на полный автомат §5; `event_log`; мягкий claim и жёсткий лок печати; замена «удалить» на `EXCLUDED` | 3–4 дня |
| **4. Печать пакета** | `print_job` с позициями; прогресс; пауза/стоп; продолжение с места обрыва; подтверждение спорных позиций | 2–3 дня |
| **5. Личные папки** | `Source.kind=personal`, клиентское сканирование локальных папок, флаг `is_local_only` | 1–2 дня |
| **6. Упаковка клиента** | PyInstaller + Inno Setup → MSI без прав администратора | 2–3 дня |

Первое рабочее демо — после вех 1+2 (~1.5 недели): сервер индексирует шару, клиент печатает с выбором принтера и лотка. Полный цикл — ~3 недели.

**Порядок вех 3 и 4 может измениться** в зависимости от ответов на блокирующие вопросы §14.
