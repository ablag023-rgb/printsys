# printsys — память проекта для Claude Code

> Этот файл читается автоматически в каждой сессии Claude Code внутри репозитория.
> Держит в контексте, что это за проект, как он устроен и какие правила действуют.
> При правках кода — сверяйся с этим файлом; при расхождениях приоритет — у кода и `docs/`.

## Текущий статус: v3.1 — документы в S3

**Спецификация:** [`docs/SPEC.md` v3.1](docs/SPEC.md) — источник истины по решениям.

**Реализовано:** индексатор двух хранилищ S3, модель `storages`/`source_objects`/`parsed_docs`,
настройка хранилищ в UI, доставка документов клиенту через сервер, периодический скан,
инфраструктура (два MinIO + идемпотентный seed).

**Аутентификация:** вход по логину/паролю (argon2id), JWT access 30 мин +
ротируемый refresh 30 дней. Все роуты закрыты, открыты только `/login` и
`/healthz`. Учётка по умолчанию из `.env` с обязательной сменой пароля.
Роли заведены в модели, RBAC-проверок пока нет.

**Windows-клиент** (`client/`) — реализован: окно оператора, подготовка дела,
печать одним заданием на дело, долговечная очередь в SQLite, per-user MSI и
переносимая раздача. Подробности — `client/README.md`.

**Интерфейс один на веб и клиент.** Окно клиента (`printsys-gui.exe`) грузит
эту же страницу в WebView2 и вызывает локальный Python через
`window.pywebview.api.*`. Всё, что умеет только клиент, помечено классом
`client-only` и живёт в `app/static/client.js`; в браузере оно скрыто, потому
что печатать может лишь машина оператора. **Второго набора шаблонов не
заводить** — ради этого всё и сделано.

**Не реализовано:** роли (RBAC), полная модель состояний дела (есть только
флаги `is_stale`/`is_orphaned`), подпись кода для клиента.

**Удалено как обесценившееся:** `mounter.py` (CIFS), `share.py` (UNC-резолв),
`folder.py` (режим одной папки), серверная сборка PDF (LibreOffice, reportlab, pypdf).

Ключевые решения (обоснования — в SPEC):
1. **Индексирует сервер, печатает клиент.** Реестр общий → индексатор должен быть один
2. **Документы доставляются через сервер** — клиенту не нужен доступ к S3, аудит фиксирует факт скачивания
3. **ETag — маркер версии, не хэш.** При multipart он `md5-of-md5s-N`; нам важно лишь, что он меняется при перезаписи. `LastModified` в триггер изменения НЕ входит
4. **Кеш парсинга по `content_etag`, а не по ключу объекта** — переименование даёт новый ключ, но тот же ETag, парсинг переиспользуется. Это заменяет inode-логику и строго проще неё
5. **Скан, а не нотификации.** Полный `list_objects_v2` каждые 5–10 мин: только он видит удаления, а нотификации теряются (at-most-once)
6. **Пометка `orphaned` только при полностью завершённом листинге всех хранилищ** — иначе обрыв связи «потеряет» реестр
7. Дело собирается по КСР **поверх всех хранилищ**: `source_objects` не знает о делах

## 1. Что это

**Система печати судебных дел** — оператор юрслужбы готовит пакеты документов для подачи в суд по долгам ЖКУ.

1. Сервер индексирует **несколько хранилищ S3** (каждая система-источник пишет в своё)
2. Группирует объекты в **дела** по коду КСР; якорь дела — «Справка о расчетах по ЖКУ» (xlsx)
3. Раскладывает по **настраиваемым слотам** (маски по имени, drag-to-reorder)
4. Клиент забирает документы **через сервер**, собирает PDF дела: титул → слоты по порядку → подвал `КСР/NN`
5. Печатает через `win32print` на локальный сервер печати
6. Ведёт статусы **напечатано** и **передано в суд**

**Стадия** — DEV/прототип, внутренняя сеть. Вход по логину/паролю есть, RBAC — нет.

## 2. Стек

- Python 3.12 + **FastAPI 0.115** + **Jinja2** + **HTMX 1.9** — SSR-веб без фронт-сборки
- **PostgreSQL 16** + **SQLAlchemy 2.0 async** + **asyncpg** + **Alembic** — БД и миграции
- **python-calamine** (основной) + **openpyxl** (резервный) — парсинг xlsx-справок
- **APScheduler** — периодический скан
- **boto3** — работа с хранилищами S3
- **cryptography** — шифрование секретов хранилищ (Fernet)
- **MinIO ×2** — симуляция двух систем-источников для разработки
- **Docker Compose** — dev (`docker-compose.yml`) и prod (`docker-compose.prod.yml`)
- **pytest + pytest-asyncio + httpx** — тесты

Сборки PDF и печати на сервере **нет** — они на клиенте (Excel COM + win32print).

## 4. Модель данных

Все таблицы — public. Ключевые сущности:

- **`app_settings`** (key/value/json) — настройки, правятся в UI. Ключи: `slots`, `labels`, `footer`, `title_page`. Дефолты в `settings_store.DEFAULTS`.
- **`storages`** — хранилища S3: `endpoint_url`, `bucket`, `prefix`, `access_key`, `secret_key_enc` (Fernet, в API не отдаётся), `health`, `object_count`.
- **`source_objects`** — индекс объектов, ключ `(storage_id, key)`: `size`, `etag`, `ksr`, `is_anchor`, `last_seen_scan_id`, `state`.
- **`parsed_docs`** — кеш парсинга по `content_etag` (PK), НЕ по ключу объекта. Переименование бесплатно.
- **`scan_runs`** — журнал: новые/изменённые/пропавшие объекты, распарсено, попаданий в кеш, длительность.
- **`cases`** (ksr PK) — дела. `slots` = `{slot_id: [{storage_id, key, name, size, etag}, ...]}`, `composition_hash`, `is_stale`, `is_orphaned`.
- **`print_history`** (id, ksr FK, printed_at, note) — аудит фактов печати.
- **`users`** — операторы: `login`, `pwd_hash` (argon2id), `role`, `must_change_password`.
- **`refresh_tokens`** — ротируемые токены, хранятся хэшем; `family_id` для отзыва всей цепочки при детекте компрометации.

Схема: миграции `0001_initial` … `0005_auth`. При правках модели — генерировать новую миграцию:
```bash
docker compose exec web alembic revision --autogenerate -m "описание"
docker compose exec web alembic upgrade head
```

## 5. Ключевые бизнес-правила (не удалять/не менять без обсуждения)

- **Парсинг справки** — основной ридер `python-calamine` (Rust), резервный `openpyxl`. **Не возвращать openpyxl как основной**: он падает с `TypeError` в `parse_col_breaks` на части реальных файлов биллинга даже в режиме `read_only`, исключение глушилось и метаданные молча оказывались пустыми (коммит `4210fc8`).
- **Значение лейбла ищется сканированием вправо** до первой непустой ячейки (до 6 колонок), а не в соседней `c+1`: в реальных справках лейбл в колонке A, значение в C, между ними merged-ячейки. Лейблы нормализуются с удалением `№` («Лицевой счет №:»).
- **Извлечение КСР** — `scanner.extract_ksr_from_spravka_name` берёт **1-е** числовое поле из имени файла-справки, применяет `ltrim('0')`. Пример: `da_0003455606_10000_..._Справка о расчетах по ЖКУ.xlsx` → КСР = `3455606`. **Не менять на 2-е поле** — это был ранний баг, зафиксирован в `SPEC.md`.
- **Матчинг файлов к делу** — файл цепляется к КСР, если в его имени встречается КСР **в любом представлении**: без нулей (`3455606`) или padded до 10 (`0003455606`).
- **Раскладка по слотам** — первый по порядку слот с matching mask. Маска = substring (case-insensitive) или `/regex/`. Не подошло никому — в catch-all «Прочее» (если включён).
- **Дедупликация: в деле только актуальная версия документа** (`app/dedup.py`). Один документ = **строго совпадающее имя файла** в пределах одного дела; актуальная версия — самая свежая по `last_modified` среди **живых** копий. Отброшенные копии не удаляются: они уходят в `cases.archived`, показываются свёрнутым блоком в карточке и **никогда не попадают клиенту** — в `/api/cases` уходит только состав. Архив **не входит** в `composition_hash`, иначе появление старой копии поднимало бы ложное `is_stale` у напечатанного дела. Реквизиты дела читаются из **актуальной** справки. Если даты копий не различают, а содержимое разное — система не выбирает сама: обе остаются в составе, дело помечается `needs_attention` («Требует внимания»). Ручного выбора версии нет намеренно.
- **Комплектность** — все `required` слоты должны содержать ≥1 файл.
- **Порядок слотов = порядок листов в PDF** и очерёдность печати. Для сшивания критично, менять только через UI.
- **Подвал `КСР/NN`** — рисуется КЛИЕНТОМ прямо на контексте принтера, светло-серым, сквозной нумерацией через все документы дела. Не PDF-overlay: единого PDF дела не существует.
- **Печать = проставление `printed_at = today`** + запись в `print_history`. Повторная печать перезаписывает `printed_at`, но история сохраняется.
- **Удаление дела** — только запись в БД; файлы в папках-источниках не тронутся. При повторном скане дело появится снова, но с чистыми статусами.
  ⚠️ **Известный дефект:** это скрытый способ стереть факт печати. В v2.0 заменяется на `EXCLUDED` (мягкое исключение с сохранением истории), физическое удаление — только админу. См. SPEC §13.

## 9. Известные ограничения v0.3

1. **Печать целиком на клиенте** — серверной сборки PDF нет и не будет. Дело печатается ОДНИМ заданием, документы отрисовываются по очереди в порядке слотов; склейки в единый PDF в пути печати нет (она осталась только в предпросмотре). Кнопок печати в веб-UI нет.
2. **Модель состояний не реализована** — пока только `printed_at`/`submitted_at`, полный автомат из SPEC §5 (NEW → CLAIMED → … + STALE/ORPHANED) сделан частично: есть только флаги `is_stale`/`is_orphaned`.
3. **Ролей нет** — вход по логину/паролю работает, но все вошедшие равны в правах. Разворачивать только во внутренней сети.
4. **Bind-mount как `ro` в prod** — контейнер не может изменить/удалить исходные документы. Загруженные через UI папки лежат в отдельном writeable volume `/data/uploads/`.
5. **Метаданные из Справки** извлекаются по конфигу лейблов — если xlsx-шаблон нестандартный, дополни синонимы в UI «Настройки → Парсинг Справки».
